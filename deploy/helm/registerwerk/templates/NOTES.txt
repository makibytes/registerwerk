Registerwerk has been installed as release "{{ .Release.Name }}" in namespace "{{ .Release.Namespace }}".

IMPORTANT — this chart will NOT start correctly until you complete the following. None of
these are automated by `helm install`, and skipping them fails silently or late (a crash-loop
with no obvious cause, or a real gap discovered only during an actual incident) rather than
failing the install itself.

1. Create the "registerwerk-secrets" Secret.
   templates/secret.yaml is deliberately commented out — this chart ships no plaintext secret
   defaults. Either install the external-secrets.io operator and uncomment that template, or
   create the Secret yourself:

     kubectl create secret generic registerwerk-secrets -n {{ .Release.Namespace }} \
       --from-literal=JWT_DEV_SECRET=... \
       --from-literal=REGISTERWERK_WALLET_MASTER_KEY=... \
       --from-literal=S3_ACCESS_KEY=... \
       --from-literal=S3_SECRET_KEY=... \
       --from-literal=MAIL_PASSWORD=... \
       --from-literal=DEFAULT_ADMIN_EMAIL=... \
       --from-literal=DEFAULT_ADMIN_PASSWORD=... \
       --from-literal=WALLETS_BACKUP_RESTIC_PASSWORD=... \
       --from-literal=CHAINCACHE_JWT_SECRET=...
{{- if .Values.chaincache.enabled }}

1a. chaincache.enabled is "true" — CHAINCACHE_JWT_SECRET above must match the
   chaincache.jwt.secret every chaincache workload in {{ .Values.chaincache.namespace }} was
   installed with (see chaincache/deploy/helm/chaincache's own "shared.jwt" values). Registerwerk
   does not deploy chaincache itself — it is chart'd and installed independently, once per chain,
   from that separate chart.
{{- end }}

   See templates/secret.yaml for the full ExternalSecret reference.
{{- if .Values.zamaRelayer.enabled }}

1b. zamaRelayer.enabled is "true" — also create the "{{ .Values.zamaRelayer.existingSecret }}" Secret.
   The zama-relayer Deployment and the backend Deployment's REGISTERWERK_ZAMA_RELAYER_API_KEY both
   read from this same Secret (see templates/secret.yaml's own comment for why they must):

     kubectl create secret generic {{ .Values.zamaRelayer.existingSecret }} -n {{ .Release.Namespace }} \
       --from-literal=OPERATOR_DECRYPT_PRIVATE_KEY=... \
       --from-literal=RELAYER_API_KEY=...
{{- end }}

2. Configure a production KEK provider for the wallet-keystore volume.
   REGISTERWERK_PRODUCTION_MODE is "{{ .Values.env.REGISTERWERK_PRODUCTION_MODE }}" — if true,
   the backend fails closed at startup (ProductionReadinessCheck) unless
   registerwerk.wallet.kek-provider is set to AWS_KMS, GCP_KMS, or AZURE_KEY_VAULT. Add the
   corresponding env vars (registerwerk.wallet.kms.key-id, etc.) to values.yaml's `env:` block.

   SoftHSM is DEMO-ONLY: the backend image ships it for the local stack, and in production mode the
   backend refuses to start with the SOFTHSM profile. Mount your PKCS#11 configuration and vendor
   client library through the generic hooks (extraVolumes, extraVolumeMounts, extraEnv,
   extraEnvFrom, initContainers, sidecars; see values-production.yaml for a commented pattern).
   Running more than one replica needs a shared signer (network HSM or KMS). For GKE the chart can
   point the backend at Google Cloud KMS (wallets.kmsSigner.enabled=true + keyVersion, Workload
   Identity, no key files): a KMS signer satisfies the production HSM/KMS requirement without a
   PKCS#11 token. For any other HSM/KMS target this chart bundles no vendor client, so production
   mode cannot boot until you choose one.

3. Install the companion backup chart — SEPARATELY, as its own release.
   deploy/helm/backup is not a dependency of this chart (a different release, potentially a
   different namespace, is a deliberate choice — see its own values.yaml comments). It backs
   up both PostgreSQL (WAL-G base backup) and the wallet-keystore volume (restic) — the latter has NO other
   backup mechanism, and losing it means permanently losing the ability to administer
   already-deployed on-chain assets. Install it with the two required cross-release values:

     helm install registerwerk-backup deploy/helm/backup \
       --set postgresql.host={{ .Release.Name }}-postgresql \
       --set postgresql.pvcName=data-{{ .Release.Name }}-postgresql-0 \
       --set postgresql.existingSecret={{ .Values.postgresql.auth.existingSecret }} \
       --set wallets.pvcName={{ include "registerwerk.fullname" . }}-wallets

3b. Database durability (database.shape={{ .Values.database.shape }}, RPO target <= {{ .Values.database.rpoTargetMinutes }} min).
{{- if eq .Values.database.shape "bundled" }}
   WARNING: the bundled PostgreSQL has NO WAL archive. Recovery stops at the last daily base backup
   of the companion backup chart (RPO up to 24 h, no point-in-time recovery). This shape is for
   dev/test. For production use a managed PostgreSQL with PITR (database.shape=managed) or
   CloudNativePG with Barman Cloud archiving (database.shape=cnpg, examples/cnpg-cluster.yaml).
{{- else if eq .Values.database.shape "managed" }}
   The managed instance must have PITR enabled (e.g. Cloud SQL point-in-time recovery with 7 days of
   transaction-log retention). The chart cannot verify that: see docs/operator/maintenance/backups.md
   for the required settings, and run scripts/pitr-drill.sh-style restores against your provider.
   Alert on WAL lag with the provider's metric or the documented pg_stat_archiver query.
{{- else }}
   PostgreSQL is operated by CloudNativePG; apply deploy/helm/registerwerk/examples/cnpg-cluster.yaml
   (adapted) and verify the WalArchiveLag alert is scraping cnpg_pg_stat_archiver_* metrics.
{{- end }}

4. (Optional but recommended) Configure a KMS-backed audit-chain signing key.
   registerwerk.audit.signing.provider is blank by default — the hash chain is still
   WORM-protected and verified, just without a signature anchored outside the database. Set
   it to GCP_KMS (only cloud with Ed25519 KMS support — see GcpKmsEd25519SigningKeyProvider's
   Javadoc) for a real external chain-of-custody anchor.

5. Required network inputs (the chart refuses to render without them): ingress.trustedCidrs,
   kong.env.trusted_ips and kong.adminAllowCidrs, plus env.REGISTERWERK_AUTH_TRUSTED_PROXIES set
   to a regex of your pod CIDR. The API ingress targets Kong, not the backend, and answers 404 for
   /actuator/* except health (README.md, "Blocking /actuator at the ingress").
{{- if .Values.zamaRelayer.enabled }}

6. zama-relayer runs with RELAYER_PRODUCTION_MODE={{ .Values.zamaRelayer.env.RELAYER_PRODUCTION_MODE }}: it refuses the environment-held KEK and plaintext
   OPERATOR_DECRYPT_PRIVATE_KEY unless RELAYER_ALLOW_ENV_KEK=true is set (logged WARN), and needs
   OPERATOR_DECRYPT_DURATION_DAYS set explicitly.
{{- end }}
